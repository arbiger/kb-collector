# Cross-Check Findings → Desktop SOP

## When This Fires

George says one of:
- 「幫我對照下 X 跟 Y」
- 「這篇跟 WarRoom 願景對照下」
- 「跟 AC 相關」
- 「看下現況跟這篇差多少」
- 「更新後有什麼想法」（指向既有 KB note）
- **「用 X 理論來分析這篇」/「在我們品牌 N 上能不能套用 X」/「結合 Z 看」（2026-06-22 新增）**

Where X is a **KB note** (in `~/Documents/Georges/Knowledge/`) and Y is one of:
- a **current project source of truth** (typically a project `README.md` or `SKILL.md` under `~/Documents/Georges/01 🎯 Projects/` or `~/.hermes/skills/`)
- a **framework / theoretical lens** George provides (e.g., Sowell 經濟學、SB7、Porter Five Forces)
- a **brand strategy / marketing document** (e.g., NuGROWS SB7 framework doc)

## Type A vs Type B — Pick The Right Workflow

| Type | Trigger | Workflow | Output location |
|---|---|---|---|
| **Type A: KB ↔ project state** | 「跟現況對照」「對得上 WarRoom 嗎」 | Default: 寫 cross-check findings 直接存 Desktop，**不要再問 George** | `~/Desktop/<date>-<topic>-cross-check-findings.md` |
| **Type B: Framework × KB × brand/project**（2026-06-22 新增）| 「用 X 理論分析這篇」「套到我們品牌 N 上」「結合 Z 看」 | **先 chat 預覽 → 詢問要不要存 Desktop note → 詢問要不要寫進 project AC** | 第一階段：chat 訊息；第二階段（George 同意後）：`~/Desktop/<date>-<framework>-x-<brand>-analysis.md`；第三階段（George 同意後）：寫進 project AC |

**Why Type B is 3-stage gate instead of 1-step:**
1. Framework 應用高度依賴內部 context（target customer LTV、競品數據、brand team 既有決策），chat 預覽讓 George 可以補 context 後再決定要不要落地
2. Cross-check findings 在「純對照」場景風險低（差異是事實），但在「framework × brand」場景風險高（framework 套用錯誤會誤導 brand team），需要 George 確認「這個分析對」再寫 disk
3. **「先 chat 預覽 → 寫 cross-check note → 寫進 project AC」是成本遞增的三層 gate**，跳過任何一層都是 commit 過早。預設走最便宜的 chat 預覽。

**Type B 的 chat 預覽 SOP（2026-06-22 驗證）：**
1. **3 鏡頭對照**：KB note 自己的觀點 × Framework 的分析 lens × Brand/project 自己的現況
2. **明確 status**：「這是 framework / lens，不是確定的診斷」
3. **自我懷疑段（voice marker）**：列出自己分析的限制、過度推論、可能被反駁的點
4. **詢問 routing 三選一**：A. 寫 Desktop cross-check note / B. 消化一下晚點決定 / C. 缺內部 context，回去補資料再做

## Why Desktop, Not KB

| Target | Purpose | When to use |
|---|---|---|
| `~/Documents/Georges/Knowledge/` | Source material + curated summaries | URLs, transcripts, long articles, George annotations |
| **`~/Desktop/`** | **Active analysis workspace** | **Cross-check findings, planning docs, retrospectives, working analyses** |

Cross-check findings are working documents. They may be referenced once during a planning cycle and then sit unused. KB is for things that get re-consulted. Desktop is the staging area for analysis.

The existing Desktop convention supports this:
- `cortex-distiller-plan.md` — implementation plan
- `PLAN-agent-cortex-and-ac-skill.md` — implementation plan
- `agent-cortex-summary-2026-06-11.md` — analysis/summary
- `PLAN-agent-squad-agent-team-framework.md` — implementation plan

## Filename Convention

`<date>-<topic>-cross-check-findings.md`

Examples:
- `2026-06-13-agent-squad-ac-warroom-cross-check-findings.md`
- `2026-MM-DD-<source-note-slug>-vs-<project-slug>-findings.md`

Kebab-case, date prefix, "findings" or "cross-check" in the name.

## File Structure

```markdown
# <date> <Source A> × <Source B> 對照 Findings

**Trigger：** <George's exact request verbatim>
**對照目的：** <1 sentence: what's being verified>

---

## 結論速覽
- 對得上：N 條
- 對不上 / 已過時：M 條
- <Source B> scope 變化：<if any>

## 對照表

| 層 | <Source A> | <Source B> 現況 | 對得上？ |
|---|---|---|---|

## 對得上的 N 條（展開）

1. <concrete mapping with section references>
...

## 對不上的 M 條（展開）

### 1. <biggest gap>
- Source A 說：<verbatim or paraphrase>
- Source B 現況：<verbatim from current source>
- 落差原因：<analysis>
- 建議：<actionable, optional>

## 三層時序結論

**第一層（架構對得上）：** ...
**第二層（時間軸有落差）：** ...
**第三層（<the actual insight George should focus on>）：** ...

## 3 條 actionable 建議（給你看，不一定動）

1. ...
2. ...
3. ...

## 附錄：對照來源

- <Source A>: `<path>`
- <Source B>: `<path>`
- <other files read>: `<path>`

---
*Generated by: Hermes (Megan Linn) on <YYYY-MM-DD>*
*Trigger: <verbatim George request, kept for future search>*
```

## Optional Sections (Use As Needed)

- **Sources of Truth 對照** — when Source A and Source B both have multiple internal documents (e.g., WarRoom = README + AC/ + 00-公司目標)
- **What was checked but not relevant** — to show work, e.g., "Looked at agent-squad/SKILL.md §Two-Stage Review; not directly comparable, skipped"
- **Pending questions for George** — open items that need a decision before the cross-check is fully resolvable

## Anti-Patterns

- ❌ **Don't put cross-check findings in KB** — even if "it would be useful for future reference". KB is for source material, not working analysis.
- ❌ **Don't copy the full Source A transcript** — link to it. Cross-check is summary + diff, not a re-host.
- ❌ **Don't ask George where to save** — Desktop is the default. Asking is friction.
- ❌ **Don't collapse 對得上 + 對不上 into a single paragraph** — table form is what makes the diff scannable in 30 seconds.

## After Writing

1. In Telegram reply, paste a 1-paragraph summary of the key finding (1 biggest gap, 1 strongest confirmation)
2. Mention the file path so George can open it from Desktop immediately
3. Don't ask "要我把這份 findings 存 KB 嗎" — that's the wrong default and contradicts the SOP

## Desktop mirror of a KB note (verified 2026-06-23)

When George says "桌面也放一份" / "桌面上也給我一份" / "Desktop 也要有" referring to a KB note he's about to create (or just created) — the deliverable is a **second copy** of the same content on `~/Desktop/`, not a different artifact.

**Default mirror contract** (when George just says "桌面也放一份" without specifying what to include):

1. **Filename**: `<date>-<topic-slug>.md` — same kebab-case + date prefix convention as the cross-check SOP above, but no required "cross-check" or "findings" suffix unless the content type warrants it (a YouTube digest mirror is `2026-MM-DD-<video-slug>.md`, not `...-cross-check-findings.md`).
2. **Path**: `~/Desktop/` (NOT `~/Documents/Georges/Knowledge/`). Even though it's the same content, it lives on Desktop because that's what George asked for.
3. **Required fields in the frontmatter** (George explicitly called out the source URL on 2026-06-23):
   - `source:` with the **original source URL** (YouTube / article / etc.) — must be the clickable form, not just "YouTube".
   - `original_kb_note:` path to the `~/Documents/Georges/Knowledge/` twin (so the two stay linked).
   - `mirrored_to_desktop:` `true` + date (so a future scan can find all Desktop mirrors).
4. **Required body sections** (so the Desktop copy is self-sufficient without opening the KB twin):
   - **Source line** at the top: full URL + title + channel/uploader + duration + view count + date accessed.
   - **Chapter timecodes** (if YouTube) — pulled from the video description's `⏱️ 章節時間軸` section. Even if the summary only covers part of the video, the chapter list gives George a navigation index.
   - **Tool inventory** (if the video is a tutorial) — pulled from the video description's `🛠️ 視頻中用到的工具` section. This is critical for AI/SaaS tutorials because Whisper transcriptions mangle tool names (see `youtube-content` SKILL.md → "Chinese-video + English AI tool names → Whisper phoneme substitution table").
5. **Content parity**: the AI summary and any George annotations should be **identical** between the KB note and the Desktop mirror. Don't "improve" one without the other. The only intentional difference is the frontmatter (KB note uses kb-collector defaults; Desktop mirror uses the desktop-mirror fields above) and the source-line body section.

**Why "桌面也放一份" is not "改寫成 working analysis"**: that's a different request ("統整為 desktop cross-check"). The plain "也放一份" is a **literal mirror** — same content, second location. Don't downgrade the summary, don't drop the transcript, don't pivot into analysis mode. Mirror = mirror.

**Why source URL must be in the Desktop copy**: KB notes inherit discoverability through Obsidian's wikilink/backlink graph; a Desktop `.md` sitting outside Obsidian is orphaned unless it carries its own source. George calls this out specifically (2026-06-23: "YouTube 連結也幫我保留在桌面的檔案裡面") — it's not optional.
